# HarnessHub 开发者指南

状态：Draft v0.1

适用对象：希望在 HarnessHub 发布 DSH 插件的开发者

## 1. 什么可以提交

v0.1 接受可安装的 DSH Bundle。按照当前 DSH 官方契约，分发包的 `package.json` 需要声明：

```json
{
  "name": "dsh-example-plugin",
  "version": "0.1.0",
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
```

补丁文件必须包含可解析的插件行，并随 npm 包、Git 仓库或 tarball 一起分发。普通依赖即使能被 `dsh plugin add` 安装，若没有 `dsh.bundle` 声明，也不会作为 Bundle 激活，因此不作为市场插件发布。

DSH 当前契约可能变化。提交页显示本平台支持的 DSH 版本和解析规则，不应只参考本文档日期。

## 2. 支持的来源

### npm（推荐用于稳定发布）

- 发布精确 semver 版本；
- 包中包含已经构建的运行文件；
- 使用 provenance、2FA 和最小发布权限；
- 不重新使用或覆盖已经发布的版本。

### GitHub

- 仓库建议添加 `dsh-plugin` topic；
- 用户安装时必须固定 commit SHA；
- TypeScript 源码若依赖 `prepare` 构建，必须提供自包含构建；
- pnpm 对 Git 构建脚本要求用户显式 `allowBuilds` 授权；HarnessHub 不会代替用户授予；
- tag 只是展示信息，实际安装引用仍解析为 SHA。

### Tarball

- 必须提供不可变下载位置、内容摘要和可验证来源；
- v0.1 可能要求人工审核；
- 不接受会在请求时产生不同内容的 URL。

## 3. 提交必填信息

- 名称、短描述、完整说明和分类；
- 来源仓库、包名、精确版本和许可证；
- DSH 兼容范围与测试环境；
- 权限/能力说明：文件、网络、进程、环境变量、凭证、浏览器、遥测；
- 安装期与运行期脚本；
- 外部服务、数据发送目的地和隐私说明；
- 原生二进制、下载载荷和动态执行；
- 变更日志、安全联系渠道和支持链接；
- 图标及截图的权利声明。

提交者必须确认：

- 有权分发该插件和相关素材；
- 许可证与第三方通知准确；
- 没有故意隐藏数据收集、安装脚本或高风险行为；
- 安全问题和重大权限变化会及时通知平台。

## 4. 版本与兼容性

- 每次发布创建不可变版本记录；
- 权限、依赖、安装脚本或数据处理变化应进入变更日志；
- 破坏性行为按 semver 提升主版本，若尚未 1.0 则在发布说明中醒目标注；
- 使用明确 DSH 范围，不建议只写“latest”；
- DSH 处于开发者预览时，维护者应尽快验证新的候选版本；
- 平台测试通过和作者自报兼容是两个独立标签。

## 5. 安全要求

- 不读取与功能无关的文件、密钥、Cookie 或环境变量；
- 默认最少权限，并解释每个敏感能力；
- 网络目的地应明确、使用 TLS，并提供关闭遥测的方法；
- 不下载后执行未固定摘要的代码；
- 不使用混淆隐藏行为；
- 不绕过 DSH 或用户的确认、权限和 Profile 边界；
- 不在日志、异常或遥测中泄露用户内容和凭证；
- 安装脚本只做不可避免的构建/安装工作，并保持可审查；
- 发现漏洞后提供修复版本、受影响范围和缓解方法。

## 6. 建议测试

- Bundle 清单和 patch 解析；
- 安装、启动、更新、卸载与重装；
- 支持的 DSH 版本矩阵；
- macOS、Windows、Linux 中实际支持的平台；
- 无网络、缺少凭证、权限拒绝、进程中断和部分失败；
- 用户 Profile 已有其他 Bundle 时的组合行为；
- 不覆盖用户已有配置，或清楚说明覆盖意图；
- 安装后 `--dump-config` 可解释；
- 敏感数据不进入日志或遥测。

## 7. 作者验证

GitHub 登录仅证明账户身份。Phase 2-C 认领现有 Registry 插件时：

1. 创建 Developer Profile；
2. 发起 Claim 并取得一次性文件路径与精确内容；
3. 将该文件提交到插件 canonical GitHub 仓库的默认分支；
4. 在挑战过期前请求服务端验证。

平台会核对稳定 repository/owner 数字 ID、默认分支、证明文件摘要和修改该路径的 commit SHA。用户名、作者显示名和 email 都不能证明归属。

后续版本可能增加：

- npm 包所有权或 provenance 证据。
- fine-grained GitHub App 的私有仓库、组织团队和直接权限验证。

“作者已验证”不会让插件免于版本扫描和社区规则。

## 8. 审核结果

可能结果：

- Published：当前版本符合发布政策；
- Changes requested：需要补充信息或修复；
- Restricted：页面可见但安装入口受限；
- Rejected：当前版本不符合政策；
- Delisted：原已发布版本因新证据停止分发。

审核通知会列出规则、事实和申诉方式。修复后的代码使用新版本重新扫描，不覆盖原记录。

## 9. 支持与资金

可以添加一个合规的第三方赞助链接。HarnessHub 不处理款项、不承诺交付、不仲裁支付争议。Plugin Requests 中的认领也不构成雇佣、托管或付款保证。

## 10. 发布前自检

- [ ] `package.json` 有有效 `dsh.bundle.patch`
- [ ] 发布包包含 patch 和运行文件
- [ ] 来源固定到精确版本/commit，摘要可验证
- [ ] 许可证和第三方通知完整
- [ ] 兼容范围与测试环境明确
- [ ] 所有敏感能力和网络目的地已披露
- [ ] 安装脚本、原生二进制和动态下载已披露
- [ ] 安装、更新、卸载和失败恢复已测试
- [ ] 有安全联系渠道与变更日志
- [ ] 图标、截图和文案有合法使用权
