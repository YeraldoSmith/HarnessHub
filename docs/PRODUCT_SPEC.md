# HarnessHub 产品规格

状态：Draft v0.1

更新时间：2026-08-20

## 1. 产品定义

正式名称：**HarnessHub**

英文定位：**Community Marketplace for AI Agent Plugins**

中文定位：**面向 AI Agent 插件生态的社区型市场平台**

HarnessHub 从 DeepSeek Harness 插件生态起步，是第三方发现、信任和本机安装入口。它不是通用 AI 应用商店，也不托管或运行用户的 Agent。

一句话定位：

> 让用户在执行第三方 DSH 代码之前，先看清来源、版本、权限、风险和维护状态。

## 2. 问题

DSH 官方目前以 GitHub 的 `dsh-plugin` topic 提供基础发现入口。仅靠仓库列表，用户仍难以快速回答：

- 这是一个可安装的 DSH Bundle，还是普通库？
- 当前版本对应哪个不可变提交或制品？
- 安装时是否需要运行构建脚本？
- 插件会引入什么能力和风险？
- 作者身份、许可证、维护状态是否可信？
- 这个版本与哪个 DSH 版本兼容？

HarnessHub 的核心价值是将这些答案放在安装动作之前。

## 3. 用户角色

### 使用者

希望发现并安全安装插件，不应被要求理解 npm、pnpm、Cordis 或 DSH Profile 的内部细节。

### 插件开发者

希望发布 DSH Bundle、证明所有权、声明兼容性、维护版本并获得反馈。

### 审核员

处理高风险提交、身份认领、举报、版权通知和申诉。审核动作必须可追溯。

### 未登录访客

可以搜索、浏览插件和开发者资料，但不能执行会产生社区内容或账户状态的操作。

## 4. v0.1 范围

### P0：必须完成

- 响应式 Web 市场和桌面应用；
- 插件搜索、分类、详情和版本页；
- GitHub 登录、个人资料和开发者身份认领；
- 从 GitHub `dsh-plugin` topic 导入候选仓库；
- 验证 `package.json` 中的 `dsh.bundle.patch` 以及补丁文件存在性；
- 展示来源仓库、许可证、精确版本、提交 SHA、制品摘要和兼容范围；
- 基础静态扫描、依赖与安装脚本提示、风险分级；
- 桌面端检测 DSH、选择 Profile、安装、验证、更新和卸载；
- 收藏、关注、评分、评论和举报的基础能力；
- 插件提交、认领、审核与下架流程；
- 第三方赞助链接；
- Plugin Requests：仅发布需求、认领和状态，不处理资金。

### P1：可以延后

- 精选集合、趋势榜单和编辑推荐；
- 兼容性众测；
- 审核透明度报告；
- 多语言内容；
- 团队开发者账号；
- 更强的动态分析或隔离测试环境。

## 5. 明确不做

- 不自建模型服务或托管 Agent 会话；
- 不代收打赏、赏金或订阅款项；
- 不允许平台远程静默修改用户电脑；
- 不把“作者已验证”“来源已验证”“扫描通过”合并成一个模糊徽章；
- 不保证插件不存在恶意行为或漏洞；
- 不复制或重新分发没有明确授权的第三方代码；
- 不以强制注册阻断公开信息浏览；
- 不在 v0.1 建设私信、动态流等泛社交能力。

## 5.1 产品原则

HarnessHub 不是：

- 普通 GitHub 插件列表；
- 泛社交平台；
- 黑箱审核平台；
- 强制注册平台。

HarnessHub 是：

- 插件生态入口；
- 用户与开发者社区；
- 开放但可信的平台。

## 6. 核心用户流程

### 发现与安装

1. 用户搜索插件或浏览分类。
2. 插件页展示作者、来源、许可证、版本、兼容性、风险和最近扫描时间。
3. 用户选择一个不可变版本；桌面端解析实际安装对象。
4. 桌面端普通模式展示将修改的 Profile、用户可理解的操作、权限/依赖变化和安装期第三方代码风险；底层命令只在开发者详情中展示。
5. 用户明确确认后执行安装。
6. 桌面端运行 `--dump-config` 等非启动验证，并提示需要重启相应 Profile。
7. 结果写入本机日志；用户可选择是否同步匿名安装成功计数。

### 开发者发布

1. 开发者使用 GitHub 登录。
2. 提交仓库或从候选仓库发起认领。
3. 平台通过 GitHub 身份或仓库挑战验证控制权。
4. 平台解析 Bundle 清单、来源、许可证、版本和兼容性声明。
5. 扫描后进入自动通过或人工审核。
6. 发布插件页；新版本重复版本级检查，不继承旧版本的安全结论。

### 举报与申诉

1. 用户选择明确原因并提交证据。
2. 系统生成案件并通知相关方。
3. 审核员记录事实、规则、决定和有效期。
4. 被处理方可以提交一次常规申诉；新的关键证据可触发复核。

## 7. 信任信息模型

每个标签只表达一个事实：

| 标签 | 含义 | 不代表 |
|---|---|---|
| 作者已验证 | 当前账户证明了对来源仓库或包的控制权 | 平台认可其全部行为 |
| 来源已验证 | 展示的版本可追溯到明确的仓库、制品和摘要 | 代码无漏洞 |
| 自动扫描完成 | 指定规则在指定时间对指定制品执行完毕 | 不存在未覆盖的风险 |
| 人工复核 | 审核员检查了列明范围 | 永久安全或官方背书 |
| 兼容性已声明 | 作者声明支持某个 DSH 范围 | 平台已实测 |
| 兼容性已测试 | 平台测试矩阵中通过 | 所有环境均可用 |

## 8. 内容与排序

- 默认搜索排序优先相关性、来源完整度、维护新鲜度和兼容性，不直接以下载量决定。
- “精选”必须是人工编辑标签，说明选择标准和更新时间。
- “趋势”使用时间窗口、最低样本量和反作弊规则，不展示虚假精度。
- 付费推广若未来出现，必须与自然结果明显分离；v0.1 不做付费排名。

## 9. 成功标准

v0.1 发布门槛：

- 一个真实开发者可完成认领、提交和发布；
- 一个新用户能在不阅读 DSH 内部文档的情况下识别风险并安装一个测试 Bundle；
- 安装失败不会让 Profile 留在无法解释的半完成状态；
- 每个公开版本都可追溯到不可变来源和扫描记录；
- 举报、下架和申诉均有可审计记录；
- 平台没有经手任何用户资金。

首批指标：

- 插件详情到安装确认的转化率；
- 安装成功率及可解释失败率；
- 已发布版本中具有不可变来源的比例（目标 100%）；
- 安全扫描覆盖率和高风险人工复核率（目标 100%）；
- 举报首次响应时间；
- 30 天内仍可兼容当前 DSH 基线的插件比例。

下载量、注册量和评论量不是单独的成功标准。

## 10. 法律与品牌边界

- “HarnessHub”是正式产品名称，不得在项目规划中自行改名；公开发布前仍需完成域名、商标和同名产品检索。
- 所有页面必须声明与 DeepSeek AI 的关系，除非未来获得书面授权，不得使用“官方”措辞。
- 使用 DeepSeek 名称、图标或其他品牌元素前，应核对其最新品牌指南。
- 插件作者必须确认拥有分发权，并提供准确许可证信息。
- 平台应具备版权通知、反通知或适用司法辖区要求的等效流程；正式条款由执业律师复核。
